项目拷打

RAG项目

我们制作的这个rag项目是一个面向求职招聘的带有rag问答的问答系统.我们可以向AI去询问我们想要求职的岗位,以及面试的技巧之类的,接受类似于pdf数据,markdown数据的上传,在后端使用mysql数据库和milvous向量数据库进行查询岗位信息和面试要点信息,然后将信息作为context传递给AI大模型生成回复.其中主要涉及的技术是RAG流程的的搭建,使用的技术栈是前端REACT,后端使用Python的fastapi模块.除了一个关于求职的AI的问答系统,我们还搭建了一系列的和求职相关的功能性平台,比如说AI面试官,职业性格测试,简历生成之类的附属功能.

其中主要实现的rag问答功能模块主要是建立了下面的分层形势:

  1. APIServer层,主要使用uvicorn运行异步python web应用,然后配置host和端口;使用fastapi模块构建一个具有REASFUL API的WEB应用,对前端的请求使用Pandatic里面的basemodel来将json数据转换为python类型并且进行json的数据格式验证,并且调用后续相应的RAG检索链进行处理返回结果.使用CORS配置跨域处理请求
  2. RAG检索链层,是这个层级中主要处理了对于每一个RAG问答请求,对其中每一个请求都配置一个检索链,使用相应的配置文件去配置在一次的rag请求链中应该使用那些模块.其中主要设计的模块是VectorDatabese模块,WeSearch模块,Format模块,Translation模块,PDF文件解析模块,Prompt模块,Extractor模块,主要的检索链的过程是首先使用Extractor提取请求数据中的history历史信息,使用format模块构造历史信息为合适的可以作为大模型context的string.再将query信息进过Translation模块翻译为英文,使用原始的query进过WebSearch模块查询出网络上的求职信息;将上传的pdf文件提取其中的关键信息,使用Extractor模块提取query中的关键字,将经过翻译的query和关键字传递给VectorDatabase模块,检索相应的top_k数量的求职记录信息,将上面所有的信息都作为Context交给Prompt模块请求使用langchain包Deepseek大模型来给出求职建议.
  3. VectorDatabase主要涉及到两个数据库:mysql和milvous向量数据库的信息检索.在进入vectordatabase之前首先会进行query的意图识别,识别query是询问求职岗位信息还是想面试技巧或者是和求职无关信息的询问,然后分别请求不同的mysql数据库表,使用python库mysql.connector连接数据库,然后里面存储这两张表的数据,一个是jobdetail存储所有求职岗位信息,一个jobcontent存储这面试技巧之类的信息.在表中有一个字段是blob二进制类型的,在python中读取后将其转换为numpy向量.然后使用sentencetransformer将英文的queryembedding为numpy向量,然后对于numpy向量进行余弦相似度的求解,排序相似度选出top_k个向量所对应的数据填充到context中.对于milvous向量数据库使用pymilvous库,就是建立docid,text明文,embedding向量的表,然后对于embedding使用L2欧氏距离查询top_k相似的text作为context.
  4. 我们的后端前端和数据库都是放到我们当时买的100块的小型Ubuntu服务器,然后接上校园网进行部署的,使用了南大校园内网的gitlab进行gitci,实现了基本的CICD,
  5. 对于AI请求呢,我们使用的是ragas库中的prompt模块,也就是pandaticprompt类,使用prompt去引导AI对于我们给定的输入格式,给出我要求格式的输出.

名词解释

fastapi:

是Python的简单高性能的Web 框架,实现了一系列的REASTFU API.

uvicorn:

uvicorn是一个ASGI服务器,用于运行pythonweb应用.

什么是跨域

跨域指的是当一个网页尝试访问不同网源的资源的时候,就会因为浏览器的同源策略的限制导致跨域的问题,一般来说浏览器要求域名,端口,协议三者完全一致才算是同源.一般解决跨域问题使用的方法是代理服务器,CORS,WebScoket等,我在项目中配置的就是CORS跨域,允许前端的IP地址和端口可以进来,没有限制header和cookie.

websocket

WebSocket 是一种在单个 TCP 连接上进行全双工通信的协议，它允许服务器和客户端在建立连接后双向实时传输数据，而不需要像传统 HTTP 请求那样每次通信都要重新建立连接。WebSocket 协议通过 HTTP/HTTPS 的 101 状态码完成初始握手后，升级为一个持久连接

前后端连接

使用像XMLHTTPRequest,AXios,fetch来配置请求的URL连接,请求header,HTTP body数据.

怎么做CICD的

修改.git里面的pre-push文件,修改里面的bash命令,建立一个在git push之前的本地集成测试,在所有的测试通过以后,本地的git命令将项目使用ssh.https推送到远程仓库中.远程仓库中触发hook钩子,根据根目录中的gitlab-ci.yam文件来构建流水线,将流水线任务推送到runner服务器中,执行gitlab-ci里面的不同阶段的脚本,完成前后端的构建,单元测试,集成测试,端到端测试,然后将构建信息传递给gitlab,将服务器中构建产物消除(在我们实践中是直接将构建产物部署到服务器中运行的),gitlab在流水线成功部署以后就将代码拼接到分支上.其中我们服务器中数据库是直接部署在数据库的,不在CICD流程中的.

C++QT项目

以下是一个基于Qt框架，与您描述的课程项目要求相符的"类异形工厂"游戏实现思路：

1. 游戏架构与核心类

  • GameState 类:

    • 该类是游戏的核心，负责管理游戏状态和逻辑。
    • [cite_start]在主循环（main 函数中的 while 循环）中，通过调用 update() 函数来更新所有游戏对象的状态，例如设备的运行、物品的移动、任务的进度等 [cite: 11, 44, 52]。
    • [cite_start]GameState 应该包含 Map、Device 和 Mine 对象，以及当前游戏任务、金币数量和全局强化状态等信息 [cite: 24, 28, 60, 65, 83, 84]。

  • Engine 类 (继承自 QWidget 或 QMainWindow):

    • [cite_start]该类负责游戏的渲染和用户交互，作为游戏窗口 [cite: 12]。
    • [cite_start]它将处理鼠标和键盘事件，例如放置设备、拖动地图和缩放视图 [cite: 33]。
    • [cite_start]使用 Qt 的绘图功能 (QPainter) 在窗口上绘制游戏地图、设备和物品 [cite: 12]。
    • 可以通过 Qt 的信号与槽机制 (signal/slot) 将用户输入（例如鼠标点击）传递给 GameState，并接收来自 GameState 的更新通知以重新绘制界面。

  • Map 类:

    • [cite_start]逻辑上表示一个 m x n 的矩形地图，可以用一个二维数组或 std::vector<std::vector<int>> 来存储每个地块的信息 [cite: 24]。
    • [cite_start]地图的布局可以从一个独立的文本文件（.txt）中加载，文件中记录了各种设备的位置和类型 [cite: 24]。
    • 每个地块都应存储一个指向其上放置的设备的指针或ID。
    • [cite_start]Map 类还应包含一个 DeliveryCenter 对象，它是一个至少 2x2 的矩阵，负责接收交付的物品 [cite: 25, 27]。

  • Device 抽象基类:

    • [cite_start]定义所有设备共有的基本属性和行为，例如速率 (rate)、位置 (position) 和方向 (direction) [cite: 33, 34, 35, 36]。
    • [cite_start]包含用于连接其他设备和处理物品的虚函数，例如 processItem() 和 receiveItem() [cite: 33]。
    • 派生类将实现具体的设备功能。

  • Mine 抽象基类:

    • [cite_start]代表待开采的产物，拥有一个价值属性 [cite: 27, 28]。
    • [cite_start]定义了不同矿物种类的共同属性，例如形状和方向 [cite: 4]。
    • 可以包含虚函数来处理切割操作。

2. 设备派生类

  • Miner 类 (继承自 Device):

    • [cite_start]代表开采器，放置在地块上进行开采 [cite: 34]。
    • [cite_start]有一个输出方向，可以将开采出的物品输出到相邻的设备 [cite: 34]。
    • 在 update() 函数中根据速率生产矿物。

  • Conveyor 类 (继承自 Device):

    • [cite_start]代表传送带，用于运送物品 [cite: 35]。
    • [cite_start]有一个传送方向 [cite: 35]。
    • 在 update() 函数中将接收到的物品沿传送方向传递给下一个设备。

  • Cutter 类 (继承自 Device):

    • [cite_start]代表切割机，占据两个地块 [cite: 37]。
    • [cite_start]将物品纵向切割，并分别从两个输出方向输出 [cite: 36]。
    • [cite_start]如果只需一半的图形，另一半需要被垃圾桶清除，否则切割机将停止工作 [cite: 36]。

  • TrashCan 类 (继承自 Device):

    • [cite_start]代表垃圾桶，可以从四个方向接收物品并永久清除它们 [cite: 40]。

3. 物品与动画

  • ShapeItem 派生类 (继承自 Mine):
    • [cite_start]代表游戏中的具体矿物，例如圆形、方形、三角形等 [cite: 4]。
    • [cite_start]存储物品的方向以及被切割后的新类型 [cite: 31]。
    • [cite_start]Qt 的 QPropertyAnimation 可以用于实现物品在传送带上传输的平滑动画效果 [cite: 93]。
    • [cite_start]当设备停止工作时，可以停止 QPropertyAnimation，使物品停滞在传送带上，实现视觉上的停顿效果 [cite: 94]。

4. 游戏功能

  • 存档系统:

    • [cite_start]设计一个自定义的文本文件格式（例如 JSON 或简单的键值对）来保存游戏状态 [cite: 72, 74]。
    • [cite_start]保存的内容包括全局强化状态、地图上设备的位置和类型、物品在传送带上的位置、以及任务进度等 [cite: 72, 74]。
    • [cite_start]实现 save() 和 load() 函数来导入和导出存档 [cite: 72, 77]。

  • 局部强化系统:

    • [cite_start]在 GameState 中定义任务目标，例如"成功交付20个物品1" [cite: 61]。
    • [cite_start]当玩家完成任务时，可以升级开采器、传送带或切割机的速率 [cite: 61, 63]。
    • [cite_start]这个强化效果应在当前游戏局结束时消失 [cite: 64]。

  • 全局强化系统:

    • [cite_start]通过消耗游戏中收集的金币，可以永久性地强化交付中心的大小、可开采地块的数量等 [cite: 67, 68, 70]。
    • [cite_start]这些强化数据应该保存在存档文件中 [cite: 72]。

  • 可视化:

    • [cite_start]在 Engine 类中，通过 QPainter 绘制地图、设备和物品 [cite: 12, 102]。
    • [cite_start]使用 Qt 的动画库实现物品在传送带上的移动效果 [cite: 93]。
    • [cite_start]为每个设备绘制一个可视化的朝向指示，例如箭头 [cite: 96]。
    • 地图的拖动和缩放可以通过重写 mousePressEvent()、mouseMoveEvent() 和 wheelEvent() 来实现。

关于 GameState 和主循环

问题： 您的项目描述中提到，在 main 函数中有一个 while 循环来调用 GameState 的 update 函数。请详细解释一下，这个 update 函数具体做了哪些事情？它如何协调不同设备（如开采器、传送带、切割机）的运行？

回答： update() 函数是游戏的核心逻辑驱动。在每个游戏帧，它会遍历地图上的所有设备 [cite:87]。对于开采器，它会检查是否达到速率阈值，如果可以，就生成一个新的矿物实例并尝试将其输出到连接的传送带上 [cite:87]。对于传送带，它会检查是否有物品在上面，如果有，就根据传送带的速率和方向，计算物品的下一个位置，并将其传递给下一个设备 [cite:87]。切割机则会检查输入端是否有可切割的物品，如果满足条件，就会执行切割操作，并把切割后的新物品输出到不同的方向 [cite:87]。这种集中式的 update 模式可以确保所有设备在每个游戏周期内都能同步更新，从而模拟出工厂的持续运转 [cite:87]。

关于设备和物品的连接与传递

问题： 您提到设备类中记录了"各个连接状态"。请具体说明，您是如何设计设备之间的连接逻辑的？当一个设备将物品传递给另一个设备时，这个过程是如何实现的？

回答： 我为 Device 抽象基类设计了输入和输出接口 [cite:87]。每个设备实例都包含一个指向相邻设备的指针或ID的集合，表示它的输入和输出连接 [cite:87]。例如，一个传送带的输出连接会指向它前方地块上的另一个设备 [cite:87]。当一个设备（比如开采器）完成工作并需要输出物品时，它会调用其输出连接指向的设备的 receiveItem() 方法，并将物品作为参数传递过去 [cite:87]。这种设计使得设备之间的逻辑解耦，每个设备只需要关注如何处理自己的输入和输出，而不需要了解整个工厂的全局结构 [cite:87]。

关于地图数据的存储

问题： 您使用了 n*m 的二维数字来表示地图，并且数据存储在独立的 .txt 文件中。您是如何解析这个文件，并将其中的数字转化为对应的设备实例的？

回答： 我编写了一个 MapLoader 类，负责读取和解析 .txt 文件 [cite:87]。该文件中的每个数字都代表一种特定的设备或地块类型 [cite:87]。例如，0 可能代表空地，1 代表开采器，2 代表传送带，依此类推 [cite:87]。 MapLoader 会逐行读取文件内容，将数字转换为整数，并根据这些整数，使用工厂模式动态地创建相应的设备实例，然后将这些实例放置到 Map 类的二维数据结构中 [cite:87]。这种方式使得游戏地图的配置和修改变得非常灵活，无需修改代码就可以创建新的地图布局 [cite:87]。

关于面向对象和泛型编程

问题： 您在简历中提到了熟练掌握 C++ 面向对象和泛型编程范式 [cite:87]。请举例说明您在项目中是如何应用这两种范式的，具体是哪些类和模块？

回答：

  • 面向对象： 我使用了面向对象来构建游戏的整体架构 [cite:87]。 Device 和 Mine 是两个重要的抽象基类 [cite:87]。所有具体的设备（如 Miner, Cutter, Conveyor）都继承自 Device 类，并重写虚函数来实现各自的功能 [cite:87]。这使得我可以统一管理所有设备，并轻松地添加新的设备类型 [cite:87]。同样，不同的矿物类型也继承自 Mine 基类 [cite:87]。

  • 泛型编程： 我广泛使用了 C++ 标准模板库（STL）中的泛型容器来管理游戏数据 [cite:87]。 例如，我使用 std::vector<std::vector<Device*>> 来存储地图上的设备，使用 std::queue<Mine*> 来模拟传送带上物品的流动，使用 std::map 来存储设备和矿物的信息，并使用 std::set 来避免重复 [cite:87]。这些泛型容器大大提高了代码的效率和可读性 [cite:87]。

关于 Qt 的应用

问题： 您提到使用了 Qt 的 QAnimation 库来实现物品传递的动画效果。请详细描述一下您是如何实现的？

回答： 对于物品在传送带上的平滑移动，我使用了 Qt 的 QPropertyAnimation [cite:87]。我为每个物品创建了一个 QGraphicsItem，并将其添加到 QGraphicsScene 中 [cite:87]。 然后，我创建了一个 QPropertyAnimation 实例，将其目标对象设置为物品的 QGraphicsItem，并设置动画的属性为 pos (位置) [cite:87]。动画的起始值是物品在传送带上的当前位置，结束值是下一个地块的位置 [cite:87]。通过设置动画的持续时间来控制物品移动的速率 [cite:87]。 当一个物品被设备接收后，我会为它启动一个新的动画，从而实现从一个设备到另一个设备的连续平滑移动 [cite:87]。

关于信号与槽机制

问题： 您在描述中提到了使用了 Qt 的 signal 和 slot 机制。请举例说明，您在项目中具体在哪些场景下使用了它？这种机制带来了什么好处？

回答：

  • 场景1： 用户交互。当用户通过鼠标点击地图来放置设备时，Engine 类的 mousePressEvent() 函数会发出一个自定义的信号，例如 devicePlaced(QPoint pos, DeviceType type)。这个信号会连接到 GameState 类的槽函数，如 handleDevicePlacement(QPoint pos, DeviceType type)。GameState 收到信号后，就会在指定的位置创建并放置相应的设备实例 [cite:87]。

  • 场景2： 游戏状态更新。当游戏任务完成或金币数量改变时，GameState 可以发出一个信号，例如 goldUpdated(int newGold)。Engine 类中的 UI 组件，如一个显示金币数量的标签，可以连接到这个信号，并在槽函数中更新显示内容 [cite:87]。

  • 好处： 信号与槽机制实现了对象之间的松散耦合 [cite:87]。Engine 不需要知道 GameState 的内部实现细节，它只负责发出信号；同样，GameState 也不需要直接调用 Engine 的 UI 更新方法 [cite:87]。这种设计使得程序架构更加清晰，易于维护和扩展 [cite:87]。

综合能力问题

问题： 在这个项目的开发过程中，您遇到的最大的技术挑战是什么？您是如何解决的？

回答： 最大的挑战是如何在逻辑更新和图形渲染之间保持同步，并确保动画效果的平滑性 [cite:87]。 刚开始我尝试将所有逻辑和渲染都放在主循环中，但这导致了明显的卡顿 [cite:87]。 我通过将核心游戏逻辑（在 GameState 中）和渲染逻辑（在 Engine 中）分离来解决这个问题 [cite:87]。 游戏逻辑在一个独立的线程中进行，而渲染则利用 Qt 的事件循环进行异步更新 [cite:87]。 通过使用 Qt 的 QTimer 定时器来周期性地触发 GameState 的 update 函数，并使用信号与槽机制将需要渲染的物品状态变化通知给 Engine，从而实现了流畅的动画和稳定的游戏帧率 [cite:87]。

问题： 您认为这个项目还有哪些可以改进或扩展的地方？

回答：

  • 扩展新设备： 可以增加新的设备，比如旋转器，可以将物品旋转90度；或者分路器，可以将物品分流到不同的传送带上 [cite:260]。
  • 增加音效和动画： 可以为设备的运行和物品的交付添加适当的音效，并为切割机和开采器添加更酷炫的动画效果，以提升用户体验 [cite:258,259]。
  • 性能优化： 当地图变得非常大、设备数量增多时，可以考虑使用更高效的数据结构或算法，比如四叉树或空间哈希，来优化物品的查询和碰撞检测，而不是简单地遍历整个地图 [cite:87]。

物品传递逻辑阻塞处理实现方案

1. 设备状态管理

在 Device 基类中，添加一个布尔类型的成员变量，例如 isBlocked，初始值为 false。这个变量用于表示设备是否因为下游设备无法接收物品而停止工作。

2. 传递物品逻辑

  • 在 Device 的 update() 函数或专门的 processItem() 函数中，当设备想要将物品传递给下一个连接的设备时，首先会检查下一个设备的状态。
  • 例如，一个传送带在将物品从A地块传递到B地块时，会先检查B地块上的设备是否能够接收物品。这个检查可以封装在一个函数中，比如 nextDevice->canReceiveItem()。
  • 如果 canReceiveItem() 返回 true，则开始物品传递的动画，并将其传递给下一个设备。
  • 如果 canReceiveItem() 返回 false，则说明下游设备被阻塞。此时，当前设备（即A地块上的传送带）将保持 isBlocked 为 true，物品会停留在当前地块上，动画也会停止或暂停。

3. 接收物品逻辑

  • 在 Device 基类中，实现一个 canReceiveItem() 函数，该函数返回一个布尔值，用于指示该设备是否可以接收新物品。
  • 对于大多数设备，canReceiveItem() 应该检查其内部的物品队列或存储空间是否已满。例如，一个传送带在同一时间只能处理一个物品，如果它上面已经有一个物品在运输中，那么 canReceiveItem() 就应该返回 false。
  • 对于垃圾桶，因为它可以随时接收物品，所以 canReceiveItem() 应该始终返回 true。
  • [cite_start]对于切割机，如果它的一条输出路径被下游设备阻塞，那么它应该将 isBlocked 设为 true，并停止工作，直到阻塞解除 [cite: 36]。

4. 动画与速率的关联

  • 使用Qt的 QPropertyAnimation 来控制物品传递的动画。
  • 当一个设备开始传递物品时，创建一个 QPropertyAnimation 实例，并根据设备的速率属性来设置动画的持续时间。例如，速率越高，持续时间越短，物品移动得越快。
  • [cite_start]当设备因为下游设备阻塞而无法传递物品时，停止或暂停相关的 QPropertyAnimation。isBlocked 状态为 true 时，物品将停止移动，从而在视觉上体现出停滞效果 [cite: 94]。

  2. 槽函数逻辑： 在 onAnimationFinished() 槽函数中，执行以下操作：

    • 更新物品状态： 确认物品已经到达了下一个设备的位置。
    • 释放当前设备： 将当前设备的物品持有状态更新为“空”，例如将一个 held_item 指针设为 nullptr。
    • 解除阻塞状态： 将当前设备的 isBlocked 状态设为 false，从而允许它处理下一个物品。
    • 通知下一个设备： 调用下一个设备的 receiveItem() 方法，正式将物品的所有权转移给它。

这个机制带来的好处：

  • 解耦： 动画和游戏逻辑之间实现了分离。动画库只负责完成动画效果，而 Device 类则负责在动画结束后更新游戏状态。
  • 同步： 确保游戏状态的更新（例如物品所有权的转移和设备阻塞状态的解除）与动画的完成精确同步。这避免了物品在逻辑上已经转移但视觉上还在旧位置的潜在问题。
  • 事件驱动： 这种基于事件（finished() 信号）的机制比在主循环中不断轮询动画状态更高效、更优雅。

C++ 高级特性与内存管理

  • 问题： 您在项目中使用 std::vector 和 std::queue 等 STL 容器。当您动态创建 Device 和 Mine 对象时，您是如何管理它们的生命周期的？例如，当您将 new Device 出来的指针放入 std::vector 时，如何确保它们被正确释放以避免内存泄漏？
    • 回答： 我会使用 C++11 引入的智能指针来管理动态分配的内存，例如 std::unique_ptr 或 std::shared_ptr。如果一个 Device 的所有权是唯一的，我会使用 std::unique_ptr<Device> 来存储它。当 std::vector 被销毁时，std::unique_ptr 会自动调用 delete，从而避免内存泄漏。如果一个 Mine 对象需要在多个设备之间共享（例如，一个 Conveyor 和一个 Cutter 都需要访问同一个 Mine 对象），我会使用 std::shared_ptr<Mine>，它会通过引用计数来管理对象的生命周期。
  • 问题： 您提到 Device 抽象基类和派生类。在多态调用中，您是如何确保正确调用派生类的虚函数？例如，processItem() 函数，您在基类中是如何定义的？
    • 回答： 在 Device 基类中，我会将 processItem() 定义为一个纯虚函数：virtual void processItem() = 0;。这使得 Device 成为一个抽象基类，无法直接实例化。每个派生类（如 Miner, Cutter）都必须实现自己的 processItem() 函数。在主循环中，当遍历 std::vector<std::unique_ptr<Device>> 并调用 device->processItem() 时，C++ 的虚函数机制会确保正确地调用到实际对象（如 Miner 或 Cutter）的 processItem() 实现。
  • 问题： 垃圾桶 TrashCan 可以从四个方向输入物品。这在您的 receiveItem() 函数中是如何体现的？
    • 回答： 在 TrashCan 类的 receiveItem() 函数中，我不需要关心物品是从哪个方向来的。这个函数的唯一作用就是接收物品并将其“销毁”，即释放内存并从游戏中移除。由于垃圾桶没有下游设备，它永远不会被阻塞，所以它的 canReceiveItem() 函数会始终返回 true。这种设计简化了垃圾桶的实现，体现了其功能特性。

软件工程与设计模式

  • 问题： 您在简历中提到项目架构清晰可扩展。请问您在项目设计中应用了哪些设计模式？
    • 回答：
      • 工厂模式（Factory Pattern）： 在加载地图数据时，我使用了工厂模式。MapLoader 类会根据 .txt 文件中的数字来动态创建不同的 Device 派生类实例。这避免了在 MapLoader 中使用大量的 if-else 或 switch 语句，使代码更易于扩展和维护。
      • 单例模式（Singleton Pattern）： 游戏中的某些全局对象，例如资源管理器或配置管理器，可以设计为单例模式，以确保整个程序中只有一个实例。
      • 观察者模式（Observer Pattern）： Qt 的信号与槽机制本质上就是观察者模式的一种实现。它让对象（观察者）可以订阅感兴趣的事件（信号），当事件发生时，它们会得到通知并执行相应的操作。这使得游戏核心逻辑和 GUI 之间的通信变得解耦。
  • 问题： 您的项目中有地图、设备、物品等多个模块。您是如何组织这些代码文件的，遵循了哪些软件工程实践？
    • 回答： 我将不同的类放在各自的头文件（.h）和源文件（.cpp）中，以实现模块化。例如，Map.h 和 Map.cpp、Device.h 和 Device.cpp 等。我会使用 include guards 或 #pragma once 来防止头文件被重复包含。在代码风格方面，我遵循了团队或个人的编码规范，使用了 clang-format 来保持代码格式一致。同时，我也使用了 git 进行版本控制，并定期提交代码，以便追踪修改和协同开发。

游戏设计与性能优化

  • 问题： 您如何处理不同设备速率（rate）的体现？例如，一个开采器的速率比传送带的速率快，这在游戏逻辑中是如何表现的？
    • 回答： 速率可以通过一个计时器或计数器来体现。在 Device::update() 函数中，我可以累加一个时间差（delta_time），当累加值达到设备速率所需要的时间时，才执行一次操作。例如，如果一个开采器的速率是每秒1个，那么每当 delta_time 累加到1秒时，它就会开采出一个新物品。如果开采器比传送带快，那么开采器可能会在传送带无法接收物品时被阻塞，从而在游戏玩法上体现出速率差异。
  • 问题： 您的游戏地图是 m x n 的矩形。当地图非常大时，您如何优化渲染性能？
    • 回答： 对于大型地图的渲染，全屏重绘效率低下。我会考虑以下优化：
      • 局部重绘： 只重绘发生变化的区域，例如有物品移动或设备放置的格子。Qt 的 QWidget::update(const QRect &rect) 方法可以实现局部重绘。
      • 脏矩形（Dirty Rectangles）： 维护一个“脏矩形”列表，记录所有需要重绘的区域。在每一帧的渲染循环中，只绘制这些脏矩形内的内容。
      • 视锥剔除（Frustum Culling）： 只渲染当前摄像机视野范围内的部分地图。通过计算可见区域，可以跳过对屏幕外的设备和物品的绘制。
      • 图层渲染： 将地图背景、设备和物品分成不同的图层进行渲染，当只有物品移动时，只需要更新物品图层，而无需重新绘制背景和设备。
